lihaiplan status

lihaiplan 的外部狀態頁

已經上線。這一頁描述的是最終狀態，不是要做什麼。

給接手的 agent。版本 1 是原始計畫，撰於 2026-08-15；本版 2026-08-16 改寫為執行結果。 對應 lihaiplan 部署 1604faf，Upptime 釘在 v1.43.14。

現在有什麼

狀態頁 status.jenlihai.website
GitHub Pages，Let's Encrypt 憑證，強制 HTTPS
Repo jerryhuangyu/lihaiplan-status（public）
Canary 計畫 5c5fg2jasp2h · drafts.jenlihai.website/d/5c5fg2jasp2h
原始檔是 repo 裡的 status-canary.html
檢查間隔 排程 5 分鐘，實測落在 15–20 分鐘

四個監控

已發佈的計畫       https://drafts.jenlihai.website/healthz
讀取一份真實計畫    https://drafts.jenlihai.website/d/5c5fg2jasp2h   ← 比對 "canary-ok"
儀表板與 API      https://plan.jenlihai.website/healthz
登入             https://auth.jenlihai.website/healthz

順序是刻意的。會來看狀態頁的人絕大多數是拿到連結打不開的讀者，不是登入使用者， 所以讀者那條路排前兩位。

第二條才是這裡最有價值的一條。 /healthz 只證明行程活著。物件儲存（MinIO）壞掉時，另外三條會全部是綠的， 而所有讀者都拿不到內容——因為計畫的位元組在 bucket 裡。

第二條走完 DNS → TLS → 反向代理 → app → Postgres → MinIO → 真的位元組， 而且不只看 200：__dangerous__body_down_if_text_missing 要求頁面內容裡真的出現 canary-ok，否則就算回 200 也記成 down。 代理回一頁錯誤頁也是 200，這一條就是為了那種情況。

為什麼是外部的

服務掛掉的時候，掛掉的東西沒辦法告訴你它掛了。 如果狀態頁由 plan.jenlihai.website 自己 serve，「app is down」這個狀態 永遠不可能被顯示出來。所以它跑在 GitHub Actions，頁面放在 GitHub Pages， 兩者都跟 lihaiplan 的主機無關。

lihaiplan 之後會有一個 /status 頁（由 app 自己 serve）。那是另一件事， 兩者互補而不是二選一：

這個狀態頁/status（尚未做）
全站掛掉時還在跟著死
粒度每個 URL 上／下元件、歷史、事件說明
事件記錄自動開 GitHub issue人手寫的說明
偵測延遲15–20 分鐘5 分鐘

最後一列值得注意：/status 若要對得起 5 分鐘這個粒度， 資料來源不能是這個狀態頁。

警報鏈驗證過了，不是假設

刻意弄壞測試做過一次，證據是 issue #1： 自動開啟、修好後自動關閉。

測試方式不是 lihaiplan disable，而是上傳一版把 canary-ok 換掉的 canary。這樣測到的東西不一樣：那次回的是 HTTP 200， issue 內文自己寫著 HTTP code: 200，證明轉紅的是關鍵字比對而不是狀態碼。 只驗狀態碼的話，那條檢查最重要的部分等於沒被驗過。

副作用：「讀取一份真實計畫」的 uptime 因此掉了一截，正在隨時間稀釋。那不是真實停機。

跟原計畫不一樣的地方

一、GITHUB_TOKEN 不可能完成原計畫的步驟 3

原計畫說把 Workflow permissions 改成 read and write 就好。改了，Setup CI 還是失敗， 而且錯誤訊息不會直說。原因是 Upptime 的 update-template 會改寫 .github/workflows/*，而 GitHub 無條件禁止 GITHUB_TOKEN 寫 workflow 檔案，跟 repo 設定無關。它是 job 的第一步，倒了之後檢查、README、 Pages 部署全部沒跑到。

updates.yml（upptime/updates）是同一類東西，每天 03:00 會用同樣 的方式失敗，而且萬一成功還會解掉版本釘選。

現在的處置：

  • update-template.yml 與 updates.yml 已刪除
  • setup.yml 裡的 Update template 步驟已移除
  • Upptime 釘在 v1.43.14，理由與手動升級方式寫在 setup.yml 開頭

另一條路是把有 workflow scope 的 PAT 放進這個公開 repo 的 secrets， 用一個長期憑證換每週自動更新。對一個狀態頁來說，釘住版本比較便宜。

不要把自動更新打開回去，除非你同時準備好那把 token。 上游在每個 workflow 檔案開頭寫著「不要編輯這個檔案」， setup.yml 的開頭已經改寫成說明為什麼這次可以編輯——不然下一個人會照上游的話改回去， 然後每天多一個紅色的 workflow。

二、排程 workflow 沒跑過就不會被註冊

這件事沒有任何地方會提醒你，症狀是「設定看起來都對，但監控從來沒跑」。 剛建好時 gh workflow list 只看得到兩個 workflow， gh workflow run uptime.yml 會回 404。

用 repository_dispatch 逐一觸發一次就會註冊：

for t in uptime setup response_time summary graphs; do
  gh api repos/jerryhuangyu/lihaiplan-status/dispatches -f event_type=$t
done

三、DNS 是 DNS-only，這是刻意的

jenlihai.website 整個 zone 在 Cloudflare，plan、drafts、 auth 都走 Cloudflare proxy。status 一開始也是（橘雲）， 但那代表狀態頁和它監控的服務共用同一層 proxy——主機死掉它還在， proxy 層出事它就跟著倒，而那正是這整件事要避免的。 

status  CNAME  jerryhuangyu.github.io   （灰雲 / DNS-only）

動這筆記錄會造成一段 HTTPS 空窗。 灰雲切換當下 Cloudflare 退出 TLS，而 GitHub 還沒簽自己的憑證，中間十幾分鐘 https:// 是連不上的。而且它不一定會自己開始簽——這次是把 Pages 的自訂網域 移除再加回去才觸發的： 

gh api -X PUT repos/jerryhuangyu/lihaiplan-status/pages -f cname=""
gh api -X PUT repos/jerryhuangyu/lihaiplan-status/pages -f cname="status.jenlihai.website"

四、原計畫漏寫的一步

原計畫說不用自訂網域時「把 cname 整行刪掉」。這不完整——上游還要求補 baseUrl: /lihaiplan-status，否則 project site 的資源路徑會壞。 我們用自訂網域，所以沒踩到，但如果哪天要退回 github.io 就會遇上。

五、帳號

repo 在 jerryhuangyu 底下。這台開發機的 gh 預設登入的是 JerryHuangDF（工作帳號），兩個都存在，弄錯不會報錯，只會把東西放到錯的地方。 repo 內設了 local credential helper 走 gh，所以切回工作帳號之後從這個 repo push 會失敗： 

gh auth switch --user jerryhuangyu

樣式

assets/lihaiplan.css 把 packages/app/src/tokens.css 的色票整套搬過來， 用 themeUrl 掛上去，取代內建的 theme: dark——內建主題都是單一模式， 而 lihaiplan 其他頁面都跟隨系統設定。

標誌全部換成 LH mark。assets/ 底下的圖檔一律從 lihai-icons 逐位元組複製、 絕不手改，所以之後要確認有沒有走鐘，cmp 一下就知道，不必用眼睛比。 原本 faviconSvg 沒設的時候，tab 上的圖是從 raw.githubusercontent.com 抓 Upptime 的 logo， 那是這一頁唯一對 GitHub Pages 以外主機發出的請求。

manifest.json、logo-192.png、logo-512.png 沒有任何設定鍵可以改，但 post-process.ts 是在 sapper export 之後才把 assets/ 蓋上去的， 所以同名檔案放進 assets/ 就會贏過產生器。這是唯一能碰到 「加到主畫面」那個介面的辦法——在那之前它叫 Upptime，圖是那支青綠色箭頭。 圖示宣告成 purpose: "any" 而不是 "any maskable"： 量過了，mark 的外角落在 80% 安全圓之外，照 maskable 裁的啟動器會把 L 跟 H 的角切掉。

mark 也放進 navbar，用的是 assets/lihai-mark.svg—— favicon.svg 深色模式會翻成 #fafafa，那條 bar 是釘死的 #faec32，翻過去就是 1.08:1，整條消失。那個檔案是 sed '/prefers-color-scheme/d' 出來的，diff 應該只有那一行。 navbar 的標題沒有隱藏，雖然只留 mark 更乾淨：Nav.svelte 的 alt 寫死是空字串，隱藏標題就會留下一個沒有名字的連結，而且無法從設定或 CSS 補。 第二個 navbar 項目因此從 lihaiplan 改叫 儀表板——本來會跟左邊的字重複，而且那才是它真正打開的東西。

masthead 的高度是照 lihaiplan 自己的狀態頁抄的， 也就是 packages/app/src/status-page.ts 裡的 .band： 14px padding、21px mark、20px/900 字，加起來 60px。抄的是這幾個數字而不是總和， 所以那邊改字級時兩邊還會一致。這是一條沒有建置流程綁著的跨 repo 依賴， 跟色票那條一樣——改了那邊，這邊不會有任何東西提醒你。

三件改的時候會踩到的事，都寫在那個 CSS 檔的註解裡：

  • 主題 CSS 在 global.css 之前載入。自訂屬性沒問題， 但一般規則在同 specificity 下會輸。檔案裡的 #sapper / main 前綴看起來像過度限定，其實不是——拿掉就會安靜地失效。
  • masthead 的文字顏色必須釘死。黃色橫幅深淺兩個模式都在， 讓它繼承 --body-text-color 的話，深色模式會是 #f0f0f0 疊在 #faec32 上，1.08:1，整條導覽列消失。同理，狀態色沒有一個是黃的： #faec32 在白底只有 1.2:1，只能當填色。
  • Upptime 的 --graph-opacity 是死的。它把變數花在 article .graph 這個後代選擇器上，但 graph 是掛在 article 自己身上的 class，永遠不匹配。反應時間曲線改用一層卡片同色的遮罩壓下去， 不能用 opacity，那會把卡片文字一起調淡。

改不到的：<meta name="theme-color"> 是產生器寫死的 #333333， 手機網址列底色還是深灰。要動就得改上游模板，會踩到刻意關掉的自動更新，不值得。

永遠不要做的事

不要刪除 canary 計畫，也不要停用它。 刪掉之後「讀取一份真實計畫」會變成永久紅燈，而那個紅燈跟服務的真實狀態無關。 設定錯誤被記成停機，是狀態頁最不該犯的錯。

要改它的內容，改 repo 裡的 status-canary.html，然後 帶著 --draft 更新同一份，不要建新的： 

npx lihaiplan upload ./status-canary.html --draft 5c5fg2jasp2h

內容裡必須保留 canary-ok 這個字串。改掉它等於宣告停機。

不要把這個 repo 併進 lihaiplan 主 repo。 每次檢查都會 commit 一次結果，一天數百個 commit，會把程式碼的歷史徹底淹掉。

已知的限制，不要試圖修

  • 偵測延遲 15–20 分鐘。排程寫的是 5 分鐘，實測不是。這是 GitHub Actions 排程的性質，不是設定問題，調 cron 沒有用。抓「掛了兩小時」很準，抓「抖了 30 秒」不行—— 而且中間掛掉又自己好了的話，很可能完全沒有紀錄。要秒級偵測就得換付費監控，那是另一個決定。
  • 檢查來源是 GitHub 的機器。它看到的是「從 GitHub 的網路看得到嗎」， 不完全等於你的使用者看得到嗎。
  • DNS 這一層仍然共用。灰雲讓「提供頁面」脫離了 Cloudflare， 但 jenlihai.website 的 NS 還是 Cloudflare，整個 zone 出事還是會一起倒。 要完全切開得把 status 換到別的網域或別的註冊商。
  • 狀態頁的內容是自動的。「06:20 資料庫磁碟滿了，已處理」這種人話要寫在 issue 裡，或等 lihaiplan 自己的 /status。

驗收結果

  • 狀態頁打得開，四個站點都顯示為 up
  • history/ 存在，commit 正在自動累積
  • Actions 沒有紅色的 workflow，六個 workflow 都已註冊並排程
  • 刻意弄壞 → 自動開 issue → 改回 → 自動關閉，實際跑過一次
  • 從手機、不同網路打開，確認不依賴任何 lihaiplan 的東西

最後一條在執行過程中證明了它的價值：正是因為真的去檢查「它依賴什麼」， 才發現整個網域共用同一層 Cloudflare proxy。沒被驗證過的監控等於沒有監控， 沒被檢查過的隔離也一樣。

由 lihaiplan 發佈。這一頁是靜態 HTML，沒有腳本，任何拿到連結的人都能直接讀。
